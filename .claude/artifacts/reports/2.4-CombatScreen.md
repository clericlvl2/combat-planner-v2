## Questions

1. No action log reaches the client (`ApiClient` has no log endpoint, the DM document carries no undo information). `undoDisabled` and «Undid: …» come from the screen's own session stack of the last 10 undoable actions it dispatched (`remember`, `undo` in `CombatScreen.tsx`); `releaseUnit` and a reissue clear it. Undo is disabled after a reload and does not cover player actions (vision says it should). Proposal: the DM document or a combat endpoint returns the newest undoable entry (action and unit name).
2. `useCombat().dispatch` resolves `void` and never rejects (`hooks/combat.ts`, `createDispatcher`). The screen treats an action as applied when the cached version moves past the action's version (`send`); a 409 refetch also moves the version, so after a 409 the row flashes and the action joins the undo stack. Proposal: `dispatch` returns whether the action was applied.
3. A successful Retry from the `network` toast is resent inside the hook; the screen never learns it succeeded (no flash, no undo entry).
4. No hook wraps `link.get` / `link.reissue`; screen-local `screens/CombatScreen/useCombatLink.ts` (`useApi`, `useQuery` key `['combat', id, 'link']`, `mutation`). Belongs in `hooks/`.
5. New `Toast` keys `presetAdded` («{{name}} added to Library», vision), `unitRemoved`, `undo` (toast button). `Toast.presetSaved` and `Toast.undoneDamage` unused by this screen; undo text from `CombatScreen.undo*`.
6. Optional props `random` (initiative rolls on Start and on add in Active) and `origin` (player URL base, default `location.origin`); stories set both.
