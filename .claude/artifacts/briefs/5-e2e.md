## Units, in this order, one commit each

Subject `test(e2e): <unit>`. One spec file per unit, `e2e/<unit-kebab>.spec.ts`.
Every test signs up its own DM with a unique e-mail, so the specs share no
state. Shared helpers go in `e2e/helpers.ts`, created in the first unit that
needs them; a later unit may extend the file.

1. `auth`: sign-up lands on an empty `/combats`. Sign-out, then sign-in with the
   same credentials. A wrong password shows the error. A guest on `/combats` is
   redirected to `/auth/sign-in`. A signed-in user on `/auth/sign-in` is
   redirected to `/combats`.
2. `combat lifecycle`:
   - create a combat; add three units (Hero, Enemy, Ally); duplicate one;
     Save as preset (toast); add a unit from the Library;
   - Start shows the turn order; Next turn through a round wrap gives round 2
     and escalation 1 (vision Transitions);
   - Undo reverts the last action, and the «Undid: …» toast shows;
   - before any other click, open and close the Sort sheet on `/combats`, then
     click New combat. This is a regression check: a closed Sheet must leave
     nothing over the page.
3. `player`: the DM shares the link, and a second browser context opens it,
   enters a name and claims a hero.
   - After Start, the player sees the turn order.
   - The player damages their own hero, and the DM sees the change without a
     reload (SSE).
   - The DM reissues the link (with confirm), and the player's old link shows
     the link-expired screen; opening the new link shows the hero unclaimed.
   - The DM deletes the combat, and the player sees Combat deleted.
4. `library`: create presets with tags. Filter by tag (any-of, combined with
   search). Change the sort; the choice survives a reload. Duplicate and
   delete a preset, with confirm.
5. `account`: switch the language in Settings, and the interface changes at
   once and stays after a reload. Rename the display name. Delete the account
   (with confirm), which lands on sign-in with the deleted-account toast;
   signing in with the old credentials then fails.

A scenario that fails on an app defect stays in the spec, marked
`test.fail()` with a one-line title suffix naming the defect. The defect goes
into `REPORT.md` Questions with file:line and the failure output. Never
`skip`, never `only`, and do not change the assertion to make the test pass.

   server's effect, not only that a click happened.
3. No process stays on 3000 or 5173 after the run, and every run uses a fresh
   temporary database.
4. Five commits with the subjects above, each inside `e2e/**` (and
   `playwright.config.ts` where the report says why); no comments; trailer as
