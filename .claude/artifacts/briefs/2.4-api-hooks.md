## Units, in this order, one commit each

1. `api client` (`feat(api): api client`), the only `packages/api` change of
   the batch:
   - `client.ts`: `API_ERROR_CODES` gains `linkRevoked`; `AuthApi` gains
     `providers(): Promise<SocialProvider[]>` and
     `socialSignIn(provider: SocialProvider, callbackUrl: string): Promise<{ url: string }>`,
     with `SOCIAL_PROVIDERS = ['google', 'github'] as const` and
     `SocialProvider`. Nothing else in the contract changes.
   - Server: `GET /auth-providers` (public, outside Better Auth's `/auth/*`
     wildcard) returns `{ providers: SocialProvider[] }`, exactly the
     providers configured in `auth/index.ts`; `socialSignIn` calls Better Auth
     `POST /auth/sign-in/social` with `{ provider, callbackURL }` and returns
     its `url` (the app navigates; the client does not touch `location`).
   - `hono-client.ts`: `errorOf` reads `{ code, message }` from the body and
     uses `code` when it is one of `API_ERROR_CODES`, the status map otherwise
     (a 409 with body code `invalid` stays `invalid`); `ERROR_CODES` maps
     `410 → 'linkRevoked'`.
   - `openStream`: on the `EventSource` `error` event the client probes the
     resource once (`play.get` for the player stream, `combats.get` for the DM
     stream); a 410 ends the stream with `onEnd({ type: 'linkRevoked' })`, a
     404 with `onEnd({ type: 'deleted', title })` where `title` is the title of
     the last delivered document (empty string when none arrived); any other
     result keeps the browser's own reconnect. Both streams.
   - Tests in `packages/api/test/` (new or extended files): body-code
     preference, 410 mapping, the stream probe for 410 and 404 on both
     streams with a fake `EventSource`, `/auth-providers` with none / one /
     both configured, `socialSignIn` returning the provider URL.
2. `Locale` (`fix(ui): Locale`):
   `packages/ui/src/provider.tsx` takes `LOCALES`, `Locale` from
   `@combat-planner/api` and keeps exporting `locales` and `Locale` under the
   same names, so no other file changes.
3. `visual height` (`fix(ui): visual height`): `packages/ui/test/visual.test.tsx`
   captures a story whose canvas is taller than 844 px at its full height;
   width stays 390. Every existing baseline stays byte-identical (run the
   `visual` project without `--update`).
4. `ApiProvider` (`feat(ui): ApiProvider`): `packages/ui/src/api/ApiProvider.tsx`
   with `ApiProvider({ client, queryClient?, children })` (creates a
   `QueryClient` with `retry: false` when none is passed) and `useApi()`
   (throws outside the provider).
5. `FakeApiClient` (`feat(ui): FakeApiClient`): `packages/ui/src/api/FakeApiClient.ts`
   implements the whole `ApiClient` in memory:
   - `new FakeApiClient({ scenario, delay = 0 })`; `scenario` seeds the
     session, combats (full `Combat`), link tokens, players, presets, tags,
     settings, configured providers and the connection state; exported
     builders in `packages/ui/src/api/scenarios.ts` (`emptyScenario`,
     `scenario({ ... })`) are what 2.4 screen stories use.
   - `combats.dispatch` and `play.dispatch` run domain `authorize` and
     `apply`, bump `version`, and push the projected document (`project` per
     viewer) to every subscriber; errors are `ApiError` with the statuses the
     server returns (409 `version`, 403 `forbidden`, 404 `notFound`, 410
     `linkRevoked`).
   - `combats.remove` ends DM and player subscribers with `deleted` and the
     title; `link.reissue` ends player subscribers with `linkRevoked`.
   - Test controls on the instance: `setConnection(state)`,
     `failNext(code)` (the next call rejects with that `ApiError`, `network`
     included), `calls` (method name and arguments, in order).
   - Unit tests `packages/ui/test/api/FakeApiClient.test.ts`: dispatch →
     subscriber gets the projected document; player never receives a field
     the domain hides; remove → `deleted`; reissue → `linkRevoked`;
     `failNext`; `delay: 0` resolves in the same macrotask.
6. One unit per hook, in this order, `feat(ui): <hook>`, files
   `packages/ui/src/hooks/<hook>.ts`: `useToasts`, `useConnection`,
   `useCombatList`, `useCombat`, `usePresets`, `useTags`, `useSettings`,
   `useAccount`. Logic that is not React (query keys, cache updates, the toast
   stack, the reconnect timer decision, the error → toast mapping) lives in
   plain functions in the same folder and is unit-tested in Node in
   `packages/ui/test/hooks/<hook>.test.ts`; the hook is a thin TanStack Query /
   React wrapper over them. Behaviour:
   - `useToasts`: a stack, newest on top; `show({ message, action?,
     duration? })`, `dismiss(id)`; durations 4 s, 8 s with an action, `null`
     stays; texts come from the `Toast` namespace (add the keys
     `combatChanged` «The combat changed. Try again.» and `reconnecting`
     «Reconnecting…» to the six `Toast.json` files; `serverUnreachable` and
     `retry` exist). `motion: 'off'` (read from `UiProvider`) starts no timer.
   - `useConnection`: the client's `ConnectionState`; after 10 s in
     `reconnecting` shows the `reconnecting` toast with `duration: null`,
     hides it on `connected` and refetches the open combat. With
     `motion: 'off'` the delay is 0.
   - `useCombat(id, viewer)`: `viewer` is the domain `Viewer`; DM reads
     `combats.open`, player reads `play.get` with the token; the SSE
     subscription writes each document into the query cache; `ended` carries
     the `ApiEndEvent` (`deleted` with title, `linkRevoked`) for the screen;
     `dispatch(action)` sends and never changes the cache itself (vision Data
     flow 11, 14); 409 → refetch + `combatChanged` toast; `network` →
     `serverUnreachable` toast with `retry` that resends the same action
     with the same id.
   - `useCombatList`, `usePresets`, `useTags`, `useSettings`, `useAccount`:
     queries and mutations over the matching `ApiClient` groups; mutations
     invalidate their list; `useSettings.update` changes the `UiProvider`
     locale at once (vision Settings); `useAccount` exposes `session`,
     `providers`, `signIn`, `signUp`, `socialSignIn`, `signOut`, `update`,
     `remove`; the toast copy named in vision for these actions is added to
     `Toast.json` (all six locales) by the unit that uses it.
